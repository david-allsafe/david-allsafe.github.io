~$ cat summary.txt

Complete network infrastructure for "Black Mirror", a fictional organization: firewall/gateway with OPNsense, internal DNS and DHCP, an Ubuntu server hosting a published WordPress portal, availability monitoring with Nagios, and security event detection with a Wazuh SIEM — all virtualized on Hyper-V, on the 10.10.10.0/24 LAN and the blackmirror.local domain.

Tested end to end: a client receives an IP via DHCP, resolves the internal domain via DNS, and reaches WordPress through the firewall, with the event landing in Wazuh — including an external access test to the portal via port-forward on OPNsense, with the LAN disabled.

~$ cat services.log

  1. 1. Firewall / gateway (OPNsense) — WAN with outbound NAT, LAN on 10.10.10.1/24, the base for every service below
  2. 2. Internal DNS — Dnsmasq on OPNsense with Unbound as recursive resolver; A and PTR records for the servers on the blackmirror.local domain
  3. 3. DHCP — 10.10.10.100–200 range on the LAN, handing out gateway, DNS and domain to clients
  4. 4. Ubuntu server (srv-core) — static IP via netplan and remote access over SSH, the base for the services below
  5. 5. Web / WordPress server (srv-web) — dedicated LAMP stack, database with a least-privilege user, Redis cache and publication via port-forward on OPNsense
  6. 6. Monitoring (Nagios) — host and service availability (PING/HTTP/SSH/disk), with the firewall monitored over ICMP as a compensating control
  7. 7. SIEM (Wazuh) — all-in-one platform with agents on the Ubuntu hosts, file integrity monitoring (FIM), log collection and vulnerability detection

~$ cat challenges.txt

Several guides assumed VirtualBox/VMware, requiring adaptations for Hyper-V: hn0/hn1 interface names instead of em0/em1 on OPNsense, MacAddressSpoofing disabled by default blocking L2 traffic, and Secure Boot rejecting the Wazuh CentOS VM's boot.

Consistent layered diagnostics (L2 → firewall → socket → client) to isolate failures — for example, a false WAN-access timeout to WordPress that turned out to be an incorrect interface selection on the host, confirmed with Test-NetConnection instead of a local curl.

OPNsense fell outside the scope of SNMP and Wazuh agents (which would require updating the firewall and have no FreeBSD agent, respectively), compensated with ICMP monitoring in Nagios.

~$ cat conclusion.txt

The model reproduces the install → manage → observe cycle of a typical SME: a single perimeter with firewall/gateway, centralized core services, a published business application, and an observability and security layer — built on separation of duties, least privilege and defense in depth.

Future improvements: VLAN segmentation, high availability on OPNsense (CARP) and on the DNS/DHCP services, HTTPS/TLS on WordPress, centralized logging with custom Wazuh alerts, and automated backups with a recovery plan.
